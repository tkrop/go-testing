# Package testing/mock

The [`mock`][mock] package provides a small, simple handler abstraction that
enables a unified, highly reusable integration pattern of mocks using different
mock libraries, e.g. [`gomock`][gomock] and [`gock`][gock].

Unfortunately, due to [`go`][go]-limits we had to sacrifice a bit of the
type-safety to allow for chaining mock calls arbitrarily during setup. Anyhow,
the offered in runtime validation is a sufficient strategy to cover for the
missing type-safety.

[go]: <https://go.dev/>
[gock]: <https://github.com/h2non/gock>
[gomock]: <https://go.uber.org/mock>


## Example usage

The [`mock`][mock] controller abstraction can be used for mocks generated by
[`gomock`][gomock] as simple as follows:

```go
func TestUnit(t *testing.T) {
    // Given
    mocks := mock.NewMocks(t)

    setup := mock.Get(mocks, NewServiceMock).EXPECT()...

    mocks.Expect(setup)

    service := NewUnitService(
        mock.Get(mocks, NewServiceMock))

    // When
    ...
}
```

The mock handler (named [`Mocks`][mocks]) is created by [`mock.NewMocks`][new]
which on calling [`Get`][get] creates singleton mock controllers on demand by
accepting the mock constructors provided by [`gomock`][gomock] in its method
calls. In addition, it provides a mock setup abstraction (named
[`mock.SetupFunc`][setup]) to simply setup of complex mock request/response
chains.

Using these features of the [`Mocks`][mock] handler abstraction you can design
the much more advanced usage patterns that are described in the following
sections.

[mocks]: <https://pkg.go.dev/github.com/tkrop/go-testing/mock#Mocks>
[new]: <https://pkg.go.dev/github.com/tkrop/go-testing/mock#NewMocks>
[get]: <https://pkg.go.dev/github.com/tkrop/go-testing/mock#Get>


## Generic mock controller setup

Usually, a new system under test must be created for each test run. Therefore,
the following generic pattern to set up the mock controller with an arbitrary
system under test is very useful:

```go
func SetupUnit(
    t test.Test,
    setup mock.SetupFunc,
) (*Unit, *Mocks) {
    mocks := mock.NewMocks(t).Expect(setup)

    unit := NewUnitService(
        mock.Get(mocks, NewServiceMock)
    ).(*Unit)

    return unit, mocks
}
```

**Note:** The [`mock.Get(mocks, NewServiceMock)`][get] is the standard pattern
to request a new or existing mock instance from the [`Mocks`][mocks] handler.
As input, you can supply any test entity factory method accepting a
[`gomock.Controller`][gomock-ctrl].

[gomock-ctrl]: <https://pkg.go.dev/go.uber.org/mock@v0.6.0/gomock#Controller>


## Generic mock call setup

Now we need to define the mock service inline or better via a function calls
following the below common coding and naming pattern, that we may support by
code generation in the future.

```go
func Call(input..., output..., error) mock.SetupFunc {
    return func(mocks *mock.Mocks) any {
        return mock.Get(mocks, NewServiceMock).EXPECT().Call(input...).
            { DoAndReturn(mocks.Do(Service.Call, output..., error))
            | Return(output..., error).Do(mocks.Do(Service.Call)) }
        ]
    }
}
```

The pattern combines regular as well as error behavior and is out-of-the-box
prepared to handle tests with detached *goroutines*, i.e. functions that are
spawned by the system-under-test without waiting for their result.

The mock handler therefore sets up a internal `WaitGroup` and automatically
registers a single mock call on each request using [`mocks.Do(...)`][do] to
notify the call completion via `Do()` and `DoAndReturn()` of the mock. For test
with detached *goroutines* the test can wait via [`mocks.Wait()`][wait], before
finishing and checking whether the mock calls are completely consumed.

**Note:** Since waiting for mock calls can take literally for ever in case of
test failures, it is advised to use an isolated [test environment](../test)
that unlocks the waiting test in case of failures and fatal errors, e.g.
by using:

```go
test.Run(test.Success, func(t *TestingT) {
    // Given
    ...

    // When
    ...
    mocks.Wait()

    // Then
})
```

A static series of mock service calls can now be expressed simply by chaining
the mock service calls as follows using a [`mock.Chain`][chain] and while
defining a new mock call setup function:

```go
func CallChain(input..., output..., error) mock.SetupFunc {
    return func(mocks *Mocks) any {
        return mock.Chain(
            CallA(input...),
            CallB(input...),
            ...
    }
}
```

[wait]: <https://pkg.go.dev/github.com/tkrop/go-testing/mock#Mocks.Wait>


## Stored mock setup arguments

Since some call arguments needed to set up a mock call may only be available
after creating the test runner, the mock controller provides a dynamic
key-value storage that is accessible via [`SetArg(key,value)`][set-arg],
[`SetArgs(map[key]value)`][set-args], and [`GetArg(key)`][get-arg].

[set-arg]: <https://pkg.go.dev/github.com/tkrop/go-testing/mock#Mocks.SetArg>
[set-args]: <https://pkg.go.dev/github.com/tkrop/go-testing/mock#Mocks.SetArgs>
[get-arg]: <https://pkg.go.dev/github.com/tkrop/go-testing/mock#Mocks.GetArg>

**Note:** As a special test case it is possible to `panic` as mock a result by
using [`Do(mocks.Panic(<#input-args>,<reason>))`][panic].

[panic]: <https://pkg.go.dev/github.com/tkrop/go-testing/mock#Mocks.Panic>


## Generic mock ordering patterns

With the above preparations for mocking service calls we can now define the
*mock setup* easily  using the following ordering methods:

* [`Chain`][chain] allows to create an ordered chain of mock calls that can
  be combined with other setup methods that determine the predecessors and
  successor mock calls.

* [`Parallel`][parallel] allows to create an unordered set of mock calls that
  can be combined with other setup methods that determine the predecessor and
  successor mock calls.

* [`Setup`][setup] allows to create an unordered detached set of mock calls
  that creates no relation to predecessors and successors it was defined with.

Beside this simple (un-)ordering methods there are two further methods for
completeness, that allows control of how predecessors and successors are used
to set up ordering conditions:

* [`Sub`][sub] allows to define a sub-set or sub-chain of elements in
  [`Parallel`][parallel] and [`Chain`][chain] as predecessor and successor
  context for further combination.

* [`Detach`][detach] allows to detach an element from the predecessor context
  ([`DetachMode.Head`][head]), from the successor context
  ([`DetachMode.Tail`][tail]), or from both which is used in [`Setup`][setup].

The application of these two functions may be a bit more complex but still
follows the intuition.

[parallel]: <https://pkg.go.dev/github.com/tkrop/go-testing/mock#Parallel>

## Generic parameterized test pattern

The ordering methods and the mock service call setups can now be used to define
the mock call expectations, in a parameter setup as follows to show the most
common use cases:

```go
var unitCallTestCases = map[string]struct {
    setup    mock.SetupFunc
    input*...    *model.*
    expect       test.Expect
    expect*...   *model.*
    expectError  error
}{
    "single mock setup": {
        setup: Call(...),
    }
    "chain mock setup": {
        setup: mock.Chain(
            CallA(...),
            CallB(...),
            ...
        )
    }
    "nested chain mock setup": {
        setup: mock.Chain(
            CallA(...),
            mock.Chain(
                CallA(...),
                CallB(...),
                ...
            ),
            CallB(...),
            ...
        )
    }
    "parallel chain mock setup": {
        setup: mock.Parallel(
            CallA(...),
            mock.Chain(
                CallB(...),
                CallC(...),
                ...
            ),
            mock.Chain(
                CallD(...),
                CallE(...),
                ...
            ),
            ...
        )
    }
    ...
}
```

This test parameter setup can now be use for all parameterized unit test using
the following common parallel pattern, that includes `mocks.Wait()` to handle
detached *goroutines* as well as the isolated [test environment](../test) to
unlocks the waiting group in case of failures:

```go
func TestUnitCall(t *testing.T) {
    t.Parallel()

    for name, param := range unitCallTestCases {
        t.Run(name, test.Run(param.expect, func(t test.Test) {
            t.Parallel()

            // Given
            unit, mocks := SetupTestUnit(t, param.setup)

            // When
            result, err := unit.UnitCall(param.input*, ...)

            mocks.Wait()

            // Then
            assert.Equal(t, param.expect*, result)
            assert.Equal(t, param.expectError, err)
        }))
    }
}
```

**Note:** See [Parallel tests requirements](..#parallel-tests-requirements)
for more information on requirements in parallel parameterized tests.


## Custom matchers

The mock package provides currently one custom matcher greatly improving the
output. Compared to the default matchers if makes finding of call differences
in large arguments very simple. The matcher can be provided on an input value
using [`mocks.Equal(want)`][equal] as follows:

```go
func Call(input..., output..., error) mock.SetupFunc {
    return func(mocks *mock.Mocks) any {
        return mock.Get(mocks, NewServiceMock).EXPECT().Call(
                mocks.Equal(input1), ..., mocks.Equal(inputN)
            ).{ DoAndReturn(mocks.Do(Service.Call, output..., error))
            | Return(output..., error).Do(mocks.Do(Service.Call)) }
        ]
    }
}
```

The output contains improved type information as well as a regular diff of
the actual and the expected value. While the default are sensible, you can
provide your own [`DiffConfig`][config] as follows:

```go
    mocks.SetArg("my-diff-config", mocks.NewDiffConfig().
        mock.Indent("  ").MaxDepth(3)...)
```

This allows to adjust the output as needed. If you need more flexibility using
the custom matcher you may use the [`mocks.Diff(name, want)`][diff]

[config]: <https://pkg.go.dev/github.com/tkrop/go-testing/mock#DiffConfig>
[equal]: <https://pkg.go.dev/github.com/tkrop/go-testing/mock#Mocks.Equal>
[diff]: <https://pkg.go.dev/github.com/tkrop/go-testing/mock#Mocks.Diff>
